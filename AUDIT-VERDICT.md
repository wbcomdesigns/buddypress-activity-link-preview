# Audit Verdict: buddypress-activity-link-preview

**Date:** 2026-07-09 (supersedes the 2026-07-03 verdict below)
**Audit type:** Live, hybrid — source review of `bp-activity-link-preview.php` (1141 lines) + `assets/js/bp-activity-link-preview.js` (736 lines) + `assets/css/bp-activity-link-preview.css`, git-log diff against the 2026-07-03 verdict, WPCS/PHPStan/a11y/enum/wiring/REST-JS-contract tool runs, and a **live AJAX call against the running site** (`https://wbcom-free.local`, logged in as admin via `?autologin=1`, real nonce, real `bp_activity_parse_url_preview` request) to prove a new finding server-side.
**Playwright MCP was not available in this session** (not present in the tool set provided), so the UX/dark-mode rendered-screen re-verification requested in the task brief was **not performed as a browser screenshot pass**. In its place: (a) the CSS file was read in full and diffed against the described change (auto-dark block removal), and (b) the one new dynamic finding below was confirmed by driving the real AJAX endpoint end-to-end rather than by static reading alone, which is stronger evidence than a screenshot would have been for that specific bug. This is a real coverage gap for pure visual/layout regressions (see "Not independently re-verified" at the bottom) and should be closed with an actual Playwright pass before this plugin is considered fully closed out.

**Strategic frame:** this plugin is being stabilized and left alone (team focus is moving to BuddyNext). The verdict below asks "is this safe to walk away from," not "what else could we add."

## Shippable? SHIP-WITH-FIXES
One new **critical, live-confirmed DOM-based XSS** was found in the composer's client-side live-preview renderer — it was missed by the prior static-only audit and is not covered by any of the July 3 sanitization fixes (those fixed the *save/render* path only; the *AJAX-response → client DOM* path was never touched). This must be patched before this plugin is truly "closed and forgotten," because it is trivially triggerable by any authenticated member simply typing/pasting a URL into the activity composer or a comment box, and the payload can come from **any external website's `<title>`/`og:title` tag** — no cooperation from the attacker's target needed beyond "post a link to my page." All five findings from the 2026-07-03 verdict are confirmed fixed (see "Verified clean" below). Everything else is Minor/Polish and does not block a stabilize-and-leave state.

## Sellable? WITH POLISH (blocked on the XSS fix first)
Once the composer XSS is patched, this is a clean, well-behaved BuddyPress addon: SSRF guard is solid, negative caching prevents render-time remote fetches, assets are context-gated, dark mode is token-driven and correctly diffed, WPCS is nearly clean (3 minor formatting nits), and PHP 7.4–8.4 compatibility is clean. readme.txt's "Proper input sanitization and output escaping" (line 93) and "Security - Scraped link titles and descriptions are sanitized before saving and escaped on output" (line 115) are accurate for the storage/render path but do not disclose that the **live-preview AJAX response itself is raw, unescaped, attacker-influenceable content** — this claim needs to stay true after the fix, not be quietly wrong.

### Not independently re-verified this pass (carried over as an open coverage gap, not a defect)
- **Rendered visual verification (light/dark, desktop/390px, hover/focus states, `.bpalp-preview-error` empty/error states)** requested in the task brief could not be performed — Playwright MCP tools were not present in this session's tool set. The CSS was read in full and confirmed structurally consistent with the described change (base rule = light defaults with `--bx-color-*` fallbacks; single `:root[data-bx-mode="dark"]` override block; no `@media (prefers-color-scheme: dark)` block present anywhere in the file — grep-confirmed zero matches for `prefers-color-scheme`). This is static confirmation the *rule was removed as described*, not a rendered-pixel confirmation that BuddyX light/dark still look correct. Recommend a follow-up Playwright pass before fully closing this plugin out.

## Verified CLEAN (confirmed fixed / confirmed sound this pass)
- **All 5 findings from the 2026-07-03 verdict are fixed and verified in the current code:**
  1. Stored/rendered description is now sanitized at save (`sanitize_text_field(wp_strip_all_tags(...))`, `bp-activity-link-preview.php:774-775, 958-959`) and escaped at output (`esc_html()`, `:1024`, `:1031`) for both the main comment-fallback save path and the render-time comment fallback.
  2. Assets (own CSS/JS + Twitter/FB SDKs) are now gated behind `bp_activity_link_preview_should_load_assets()` (`:132-146`) and only enqueue on activity contexts, not sitewide (`:151-153`).
  3. Render-time comment fallback now calls `bp_activity_link_parse_url($url, true)` (`cached_only = true`, `:948`) — no live external HTTP fetch during page render; `bp_activity_link_parse_url()` negative-caches parse failures for 15 minutes (`bpalp_failed` sentinel, `:352-354, 542-546`) so slow/blocked URLs are not re-fetched on every view.
  4. JS AJAX handler now surfaces `response.error` via `showPreviewError()` (a `role="alert"` notice, text-escaped via `.text()`) — `assets/js/bp-activity-link-preview.js:214-234, 291-293`.
  5. `dashicons` is explicitly enqueued (`bp-activity-link-preview.php:157`); the dead `.loading` CSS selector is gone (grep-confirmed zero matches in current CSS).
- **Recent CSS change (this session's stated scope) is structurally correct:** no `@media (prefers-color-scheme: dark)` block remains anywhere in the file (grep-confirmed); a single explicit `:root[data-bx-mode="dark"]` block carries all dark-mode token overrides, consistent with the described "auto mode defers to theme tokens" intent.
- **AJAX endpoint auth/nonce/SSRF guard on the server side is solid:** `is_user_logged_in()` hard-gate before nonce check (`:203-205`), `wp_verify_nonce('bp_activity_link_preview_nonce')` (`:208-211`), `FILTER_VALIDATE_URL` + host blocklist for private/loopback/RFC1918 IPs (`:222-229, 261-281`) before any fetch is attempted. Live-tested: a request with a malformed/blocked host is correctly rejected before any remote fetch.
- **Short-URL redirect resolution re-validates the resolved host against the same SSRF guard** before following it (`:339-341`) — this was the 2026-07-03 hardening commit (`9239f95`) and is intact.
- **PHP 7.4–8.4 compatibility: clean** (`mcp__wpcs__wpcs_check_php_compatibility`, zero deprecated/removed-feature/syntax issues).
- **Version strings consistent** across plugin header (`Version: 1.7.4`), `BP_ACTIVITY_LINK_PREVIEW_VERSION` constant, `readme.txt` (`Stable tag: 1.7.4`), and `package.json` (`"version": "1.7.4"`).
- **No em-dashes in user-facing/translatable strings** (only in code comments, which are not customer-facing).
- **Text domain is consistently `buddypress-activity-link-preview`** throughout — no mismatched domains found.
- **Enum consistency, REST/JS contract, and wiring-completeness checks:** all clean/skipped-as-expected (this plugin has no own REST routes and no admin settings, so those checks correctly no-op; `mcp__wp-plugin-qa__wppqa_check_enum_consistency` returned zero issues).
- **REST embed** (`bp_rest_activity_prepare_value` filter) reads the same already-sanitized activity-meta values used by the render path — no separate escaping gap there (it returns raw meta into a JSON API response, which is the correct behavior for a REST payload; the consuming client is responsible for escaping on render, same as any WP REST field).
- **Multi-platform stand-down logic (BuddyBoss native preview, Youzify wall preview)** is intact and unchanged — de-dupe checks present in both the enqueue localization and the content-body filter.

## Scores

| Lens | Grade | Notes |
|------|-------|-------|
| Security | **D** | Solid server-side AJAX auth/SSRF guard and now-fixed save/render sanitization are undermined by a **live-confirmed, easily-triggerable DOM XSS** in the composer's client-side preview renderer (#1) — this is worse than the prior verdict's finding because it requires no save/publish step and is triggerable by any external page's metadata. |
| Performance | **A-** | Both 2026-07-03 Major findings (sitewide third-party SDK load, unbounded render-time remote fetch) are confirmed fixed: context-gated enqueue, negative caching, `cached_only` render mode. No new performance issues found. |

Actual rendered-pixel confirmation (light/dark, mobile) was not possible this session (no Playwright) — grade reflects code inspection only, not a rendered pass. |
| QA / contract wiring | **A-** | AJAX action/handler/nonce names match cleanly; the prior swallowed-error bug is fixed; only the orphaned `ajaxurl`/`enable_comments` localized values remain (#2, cosmetic). |
| Standards (WPCS/PHPStan) | **B+** | 3 WPCS issues left (down from 7), all auto-fixable/cosmetic. PHP 7.4-8.4 compatibility clean. PHPStan could not be meaningfully scored — no WordPress stubs are configured locally, so the level-5 run reports ~190 "function not found" false positives for core WP functions; this matches the plugin's own CI, which runs PHPStan with `continue-on-error: true`. |

## Bottom line for the "stabilize and leave alone" decision
Do **not** tag/release this version as-is. Patch finding #1 (a small, contained JS-only escaping fix — no new surface area, no refactor) and re-run this audit's #1 item to confirm the fix, then this plugin is in a genuinely clean, walk-away-safe state. Everything else (2-5) is safe to leave as documented technical debt; none of it needs to block the leave-alone release once #1 is closed.
