# Audit Verdict: buddypress-activity-link-preview

**Audit type:** Static, read-only (contract audit + security + performance + UX-token drift + i18n + three-entry-points). No browser tools used per instructions. Branch `v1.7.4`, code already shows `Version: 1.7.4` in header/define/readme (QA card version-bump fixes appear applied).

## Shippable? WITH FIXES
Core flow (compose-time AJAX preview, save, render, BuddyBoss/Youzify de-dupe, REST embed) is functionally sound and the primary SSRF guard on the AJAX endpoint is solid. But there is one real stored-content-integrity gap (unsanitized/unescaped description on a secondary code path) and one confirmed sitewide performance regression (3rd-party SDKs + no page-type guard) that should not ship as-is.

## Sellable? WITH POLISH
The readme's "Is the plugin secure? … Proper input sanitization and output escaping" (readme.txt:78-84) is not accurate for every code path (see #1). A paying customer running a large community would also notice global Twitter/Facebook SDK loads on every page (#2) hurting Core Web Vitals sitewide, not just on activity pages.

## Findings (ranked: Blocker → Major → Minor → Polish)

| # | Severity | Lens | Finding | File:line | Suggested journey to fix |
|---|----------|------|---------|-----------|--------------------------|
| 1 | **Blocker** | Security (stored content) | Comment-fallback auto-extraction path saves scraped `title`/`description` to activity meta **without any sanitization** (`sanitize_text_field`/`wp_kses`), and the shared renderer never escapes `description` on output (only `title` gets `esc_html`). `description` is built from `og:description`/meta `content` via `html_entity_decode(..., ENT_QUOTES, 'utf-8')`, which double-decodes entities and can turn an attacker-crafted double-encoded payload on a remote page into literal markup once decoded. Exploit path: any authenticated member posts a comment containing a raw URL (not via the composer's JS-populated hidden fields) → `bp_activity_link_preview_save_link_data()` elseif-branch (comment fallback, no sanitize call) fetches the page server-side and stores the raw decoded description → `bp_activity_link_preview_render_preview()` echoes it unescaped into the activity stream for every visitor. Contradicts readme.txt:78-84's "Proper input sanitization and output escaping" claim. | `bp-activity-link-preview.php:417` (double-decode), `:707-716` (unsanitized save), `:889-899` (identical unsanitized save in render-time fallback), `:969` (unescaped output) | `/wp-security-review` then `/bug-fix` → wrap description save with `sanitize_text_field()`/`wp_kses()` on both fallback branches, and wrap render-time output in `esc_html()` (or `wp_kses_post()` if any markup is intentionally allowed) |
| 2 | **Major** | Performance / Big-Site readiness | `bp_activity_link_preview_enqueue_scripts()` is hooked to `wp_enqueue_scripts` with **no page-type guard** (`bp_is_activity_component()`, `bp_is_user_activity()`, etc.) — it loads the plugin's own CSS/JS **plus the Twitter widgets.js and Facebook SDK** on every single frontend page of the site (shop pages, static pages, anything), not just BuddyPress screens. This is an unconditional third-party-script load sitewide: real Core Web Vitals cost + third-party cookie/tracking exposure without consent gating on pages that never render an activity stream. | `bp-activity-link-preview.php:85,126-130` | `/wp-performance` → add a `bp_is_activity_component() \|\| bp_is_group() \|\| bp_is_user_activity()`-style guard before enqueueing, and only load Twitter/FB SDKs when a preview actually needs native embeds (lazy-load) |
| 3 | **Major** | Performance / Big-Site readiness | Render-time comment filter `bp_activity_link_preview_comment_content()` has a **live external HTTP fetch fallback that runs during page render** (not just at save time) whenever cached comment-preview meta is empty — it calls `bp_activity_link_preview_extract_urls_from_content()` + `bp_activity_link_parse_url()` synchronously inline with rendering. Combined with `bp_activity_link_parse_url()` only calling `set_transient()` on **success** (no negative/failure caching), any comment whose URL is slow, blocked, or unreachable will re-attempt a full remote fetch (up to 15s timeout, `wp_safe_remote_get`) on **every page view by every visitor** until it happens to succeed. On an activity stream with many comments containing links, this is an unbounded, uncached, synchronous-external-request-per-render pattern — a direct Big-Site-readiness violation (checklist item: "Caching + invalidation," "no per-row remote calls in render loops"). | `bp-activity-link-preview.php:850-906` (render-time fallback), `:481-486` (transient only set on non-empty result) | `/wp-performance` → move all extraction/fetch to save-time only (already exists at `:696-719`) and delete the render-time fallback, OR add negative-result caching with a short TTL to stop repeat fetches per view |
| 4 | Minor | Contract audit (JS↔PHP) | PHP AJAX handler returns `wp_send_json( array( 'error' => ... ) )` for invalid/blocked-host/empty-result cases (3 distinct messages). JS success handler only checks `response.success` (true path) or `!response.error` (legacy path) — when `response.error` is set, **neither branch fires**, so the user-facing error message is silently swallowed; no UI feedback is ever shown for a blocked/invalid URL. | `bp-activity-link-preview.php:188,197,204` (PHP writes `error`) vs `assets/js/bp-activity-link-preview.js:265-270` (JS never reads `response.error`) | `/action-audit` → add an explicit `else if (response && response.error) { showError(...) }` branch in the AJAX success handler |
| 5 | Minor | CSS/UX-token drift (dead markup targets) | Icon-only buttons render `<i class="dashicons dashicons-no-alt">` etc. in JS-generated HTML, but the plugin never enqueues the `dashicons` stylesheet (`wp_enqueue_style('dashicons', ...)` absent from `bp_activity_link_preview_enqueue_scripts()`). Dashicons is only guaranteed loaded on the frontend when the admin bar is showing for the current user; for logged-in members with the toolbar disabled (or any other page-load path that doesn't pull dashicons in), close/nav icons render as invisible/empty glyphs. Separately, CSS rule `.activity-comment-link-preview-container.loading::after` (readme'd as a "Loading preview…" state) targets a `.loading` class that is never added anywhere in the JS — dead CSS. | CSS: `assets/css/bp-activity-link-preview.css:492-508`; JS icon markup: `assets/js/bp-activity-link-preview.js:360,499` (uses `dashicons` classes); enqueue: `bp-activity-link-preview.php:126-130` (no dashicons enqueue) | `/ux-audit` → enqueue `dashicons` explicitly (or swap to Lucide per design system), and either wire `.loading` class toggling in JS or delete the dead CSS rule |

### Additional lower-priority notes (Polish, not separately ranked)
- `wp_localize_script` ships `ajaxurl` and `enable_comments` in the `bp_activity_link_preview` object, but JS never reads either (`assets/js/bp-activity-link-preview.js`) — it uses the bare global `ajaxurl` instead (relies on BuddyPress's own frontend localization defining it) and has no client-side comments on/off gate. Orphaned localized data; low risk since BP typically defines `window.ajaxurl`, but fragile.
- Several JS click handlers (`#activity-url-prevPicButton`/`#activity-url-nextPicButton`/comment variants, `assets/js/bp-activity-link-preview.js:544,568,596,623`) declare a local `var bp_activity_link_preview = getLinkPreviewStorage(...)` that **shadows** the global localized `bp_activity_link_preview` object for the rest of that closure — works today because those handlers don't need the global's nonce/flags afterward, but it's a naming collision waiting to break silently on the next edit.
- `sslverify => false` is explicitly set for same-site HTTP requests (`bp-activity-link-preview.php:379`) — disables TLS cert verification even though it's same-origin; low real-world risk but a flagged anti-pattern in strict security review.
- Own SSRF regex blocklist (`bp_activity_link_preview_is_blocked_host()`, `:230-250`) does not explicitly cover the `169.254.0.0/16` link-local range (cloud metadata endpoints) or IPv6 loopback/ULA; likely covered as defense-in-depth by WP core's `reject_unsafe_urls` inside `wp_safe_remote_get()`/`wp_safe_remote_head()`, but the plugin's own guard has a documented gap worth closing explicitly.
- WPCS: 7 errors / 2 warnings on the main file — missing `translators:` comments for two `sprintf(__())` calls with placeholders (`:582,626` — genuine i18n gap, not just style), one non-Yoda comparison (`:696`), one leftover commented-out `preg_match_all` line (`:737`), plus minor whitespace/comment-punctuation issues. PHP 7.4–8.4 compatibility check: **passed clean**.
- `audit/manifest.json` still records `version: "1.7.3"` (stale from the 2026-06-05 onboarding pass) while the code now reads 1.7.4 — manifest drift, refresh via `/wp-plugin-onboard --refresh` per this plugin's CLAUDE.md convention.
